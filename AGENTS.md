# AGENTS.md — SplitSentinel

Technical guide for coding agents building SplitSentinel. Read this before changing anything in the repo.

## 1. What SplitSentinel does

SplitSentinel is a **UiPath Maestro Automate Flow** (short-running Flow, not BPMN). It runs each time a purchase requisition (PR) is submitted, and checks whether that PR plus recent related PRs are one purchase that was split to stay under an approval threshold.

Pipeline per PR:

1. Load the PR and its context (approval matrix, PRs from the last 30 days, requester, vendor, blanket POs) from Data Fabric.
2. Score the group with **deterministic rules** (script node).
3. Low score → release the PR. Otherwise → an **inline agent** judges whether the group is one need.
4. **Validate** the agent's output against the input. Apply a **guardrail**: the agent can never clear a high-risk case on its own.
5. If needed, ask the requester to justify, then re-run the agent with the justification.
6. Create an **Action Center task** for the approver of the **combined** amount's tier.
7. Apply the decision (update PR status), write an audit `SplitCase` record, and send an email notification.

**Principle:** fail closed. Any failure or uncertainty ends in a hold or a human decision, never an auto-approval.

## 5. Flow build loop

Run the SDK verbs **from the Flow project folder** `SplitSentinel/SplitSentinel/`. Run solution verbs from `SplitSentinel/`.

```powershell

Set-Location SplitSentinel
uip maestro flow init SplitSentinel --automate --sdk-source
```
- `--automate` makes it a Maestro Automate project. **Do not omit it.**
- **Do not hand-write the flow skeleton.** The scaffold assigns the flow id; keep `flow("<id>")` as generated.

### Edit → verify loop (after every source edit)
```powershell
# in SplitSentinel/SplitSentinel/
uip maestro flow check .flow-sdk/SplitSentinel.flow.ts --source --output json
uip maestro flow compile .flow-sdk/SplitSentinel.flow.ts -o SplitSentinel.flow --output json
# from the repo root
node tools/postcompile.js SplitSentinel/SplitSentinel/SplitSentinel.flow       # errorHandlingEnabled + content-based form schemaIds
# in SplitSentinel/
uip maestro flow validate "SplitSentinel/SplitSentinel.flow" --output json      # must be Data.Status = "Valid"
```
- **Never save the flow from the designer canvas.** With the flow open, the designer re-saves the compiled `.flow`: it moves each coded-app task's `completed` edge onto the first outcome port (other buttons lose their path) and drops `errorHandlingEnabled`. Its "Outcome … has no downstream node" warnings on app tasks are expected; the runtime routes on `completed` + `Action`. If the file changed, restore it with `git checkout` or recompile.
- **Do not run `uip maestro flow format`.** The canvas layout is hand-authored in the source (`LAYOUT`: lanes, positions, pinned edge routes) and `format` replaces all of it.
- `tools/postcompile.js` works around an SDK 6.74.2 issue: with `.layout(...)`, compile leaves `inputs.errorHandlingEnabled` unset on some `.onError` sources (the agent steps), and validate rejects their error edges. The script sets the flag only on nodes that have an `error` edge.
- Treat `Data.Warnings` as failures, unless they are reviewed shared-connection advisories.
- Exactly one `SplitSentinel.flow` may exist, at `SplitSentinel/SplitSentinel/SplitSentinel.flow`.

## 6. Flow SDK conventions

- Node reference: `~/.uipath/.skills/skills/uipath-maestro-flow/references/<node>.md`. Look up exact signatures in the installed package's `dist/api-members.md` / `dist/api-index.md`. Read the `.d.ts` spans, never `dist/*.js`.
- Flow-level types: use only `types.string | number | boolean | object | array | file`. Write dates as `types.string` (ISO 8601) and integers as `types.number`.
- Expressions: `input(name)`, `v(name)` (flow var), `out(step, path?)`, `err(step, field?)` (only inside `.onError`), `ran(step)`, `lit(value)`, `` js`…` ``, `` tmpl`…` ``.
- Scripts read prior outputs as `$vars.<step>.output.<field>` and must `return` a value.
- Use `.return(...)` to end a path and `.terminate(...)` to end the whole run. Bind every declared output on **every** path.
- **Inline agent:** describe each field in `returns`. **Never ask the model for JSON text** (it packs the answer into one string). Prompt variables are `{{input.<name>}}`, bound via `inputs`.
- `script()` returning fixed values must never stand in for a real capability. Use `mock()` only when a capability is proven absent.

### Node types used by SplitSentinel
| Purpose | Builder | Reference |
|---|---|---|
| Manual start (default root; inputs `requisitionId`, `whatIf`) | `.trigger(manual())` + `.input({ requisitionId, whatIf })`; first shared step `resolveRun` sets vars `prId` / `dryRun` | `manual-trigger.md` |
| Start on PR created (second root `onPrCreated`) | `.entryPoint('onPrCreated', onEvent(RecordCreated, { where: { entityScope: lookup(…).byDisplayName('Tenant'), tenantEntityName: lookup(…).byDisplayName('PurchaseRequisition') }, connection: 'dataFabric', folder: 'shared' }))`. `record-created` is a **curated** event (object built in, no `object:`); its output is only the record `Id`, so the prefix reads the PR to get `prId`. Webhook mode: needs a deployed solution to fire | `event-trigger.md` |
| Read / create / update records | `dataFabricRead` / `dataFabricCreate` / `dataFabricUpdate` (`resultMode: 'multiple'`, `limit` ≤ 1000) | `data-fabric.md` |
| Rule engine, output validation, tier lookup | `script(...)` | `script.md` |
| Split judgement | `inlineAgent(...)` | `inline-agent.md` |
| Routing | `.switch(...)` / `.branch(...)` | `switch.md`, `branch.md` |
| Approver review and requester justification | `hitl({ variant: 'quick-form', ... })` (one exit per outcome; route with `.stepSwitch`) | `hitl.md` |
| Fail-closed paths | `.onError(...)` on script and agent steps only. **`core.datafabric.read` has no error port** (`ONERROR_NO_ERROR_PORT`) | `error-handling.md` |
| Apply status to several PRs | `.loop(name, collection, body)` with `dataFabricUpdate({ record: { byId } })` | `loops.md` |
| Email notifications | `connector(SendEmail, { To, CC, Subject, Body, SaveAsDraft: true }, { connection: 'gmail', folder: 'shared' })`; saved as **drafts**, skipped on what-if runs, `.onError` continues | `connector-params.md` |

### What-if mode
`whatIf: true` on the manual root sets `dryRun`: the idempotency and "only Submitted PRs" checks are skipped, no PR status is changed, no email is drafted, and the audit row is written as `WHATIF-<prId>-<epoch ms>`. Use it for evaluation re-runs and tuning comparisons.

### Connector descriptors
`uip maestro registry prepare` writes descriptors to `.flow-sdk/connectors-local/`; import from there (`./connectors-local/<key>.ts`). Prepared so far: `uipath-uipath-dataservice` `record-created` (with `--resolve entityScope:displayName=Tenant --resolve tenantEntityName:displayName=PurchaseRequisition`) and `uipath-google-gmail` `send-email`.

### Flow evaluations
Eval set **"Guardrail and failures"** (project assets under the Flow project) uses Static simulations of the `judge` / `judgeRetry` agent steps and the `Path exact match` evaluator on the `path` output. Run: `uip maestro flow eval runs start --set "Guardrail and failures" --path .` from `SplitSentinel/SplitSentinel/`. Human tasks still appear and must be completed.

### Canvas labels and annotations
- Every step, branch, switch, loop and trigger has a business-readable `label` (`{ label: '…' }` in its options). **Labels are display-only; never rename a step id** — ids are referenced by `out()`, the eval simulations (`judge`, `judgeRetry`) and the run log.
- Branch arms carry edge labels with `.label('…')`; switch cases use `label` on the case. Human-task (`stepSwitch`) arms can't take one — the outcome name already labels the exit.
- Canvas annotations are the `NOTES` sticky notes (`.stickyNotes(NOTES)`), one per section. They are inert.
- Layout (`LAYOUT`, via `.layout(LAYOUT)`): main path on y=320 with 240 px columns; release outcomes in lanes above (pinned edge routes drop them into `reviewNeeded`); retry / requester / approver paths in lanes below; terminal ends in the bottom lane. Children of the loop container are positioned relative to it. Keep labels to 1–3 words so they fit under a 96 px node. After any layout change, check that no node, label area or note overlaps and that no edge crosses an unrelated node.

### Explain app (coded Action App `SplitSentinelExplain`)
- Second in-solution app for the requester step, same React base and styles as the review app. Inputs from `askCard` (message, amount, tier, `relatedPrs` table); output `justification` (Submit needs ≥ 20 characters); outcomes `SubmitExplanation`, `MergeMyPRs`. The `requesterDecision` switch routes on `out('requesterTask', 'Action')`; unknown answers go to approver review (`requesterUnknown`).

### Review app (coded Action App `SplitSentinelReview`)
- In-solution project `SplitSentinel/SplitSentinelReview/` (created with `uip codedapp init --type Action`, registered as `AppV2`): React + TypeScript in `source/` (Vite, `base: './'`), built to `source/dist`, the bundle the solution packs. No UiPath SDK services, so no OAuth client; it only uses `@uipath/coded-action-app`.
- Data contract: `SplitSentinelReview/action-schema.json` (validate with the coded-apps skill's `scripts/validate-action-schema.js`). Inputs include `relatedPrs` and `signals` arrays rendered as tables; output `comment` (required); outcomes `MergePRs`, `KeepSeparate`, `Reject`, `NotASplit`.
- The Flow reads the app's key and schema at compile time from `resources/solution_folder/app/codedAction/SplitSentinelReview.json` and the schema file, and binds every app input to the `reviewCard` field of the same name. Change the schema and `REVIEW_CARD_CODE` together.
- An app task has one `completed` exit; the button arrives as `out('approverReview', 'Action')` and the `approverDecision` switch routes it. Unknown values go to `decUnknown` (PR on hold).
- Button tooltips live in the app (`Form.tsx`, `outcomes[].tip`); styles in `SplitReview.css` use the template's tokens only.

### Action Center forms
- Form text is built in script steps (`reviewCard`, `askCard`) using `FORMAT_FNS` (₹ Indian grouping, short dates, role names; the script runtime has no `Intl`).
- Every shown text field uses `controlType: 'textarea'` so nothing is cut off; key figures sit side by side with `colSpan: 4`. The card width is fixed by Action Center (no SDK setting), so keep texts short; the requester's explanation is hidden by a `visible: false` rule when empty.
- Quick-form outcomes can't carry tooltips or descriptions (an outcome is only a name). Each form therefore ends with a read-only "What each button does" field just above the buttons. Real tooltips would need a coded Action App (`hitl({ variant: 'action-app' })`).
- Outcome names are the routing values: change them only through `REVIEW_OUTCOMES` / `ASK_OUTCOMES`. RFQ wording comes from the approval matrix, never from the agent.
- **Form changes need a new `schemaId`.** Compile derives a form's `schemaId` from the flow and step ids only; Action Center keeps rendering the form first registered under that id (old fields and buttons over new data, and old button names then match no route). `tools/postcompile.js` re-derives the id from the form's fields and outcomes, so always run it after compile.

### Gotchas found while building
- A `shared` input variable must not have the same name as the input (`SHARED_INPUT_TARGET_IS_INPUT`).
- Scripts must read `$vars.<step>.output`, never `$vars.<step>` (`STEP_READ_WITHOUT_OUTPUT`).
- Human-task field `value`s must be variable paths. Compute display text in a script step first (`HITL_FIELD_VALUE_NOT_PATH`).
- When inlining `rules/score.js`, strip its `module.exports` footer, and declare the rules step's `returns` map, or `validate` warns.
- Data Fabric rejects `''` for a `DATETIME_WITH_TZ` field at run time.
- Maestro Flow human tasks have **no timeout or SLA**. SLA escalation lives in Action Center, not the Flow.

**Existing tenant connections (both default and enabled):** UiPath Data Fabric (`uipath-uipath-dataservice`) and Gmail (`uipath-google-gmail`).

## 7. Agent configuration

- **Model:** `anthropic.claude-sonnet-4-6` for the split judgement. Use `anthropic.claude-haiku-4-5-20251001-v1:0` for cheap smoke tests. List what's available with `uip agent model list --output json`.
- **Temperature:** low (0–0.2).
- **Policy grounding:** inline the policy text (`data/policy/procurement-policy.md`) in the system prompt. Optionally use a Context Grounding index (see the `inline-agent.md` *Context grounding* section).

### Agent inputs (bound via `inputs`)
`anchorPr`, `candidatePrs`, `ruleResult`, `approvalMatrix`, `vendor`, `requester`, `blanketPos`, `requesterJustification` (nullable).

### Agent `returns`
| Field | Type | Values / meaning |
|---|---|---|
| verdict | string | `SPLIT` \| `LIKELY_SPLIT` \| `NOT_SPLIT` |
| confidence | number | 0–1 |
| patterns | array | subset of `P1`…`P8` |
| relatedPrIds | array | PR ids, **only ids present in the input** |
| combinedAmount | number | INR sum of related PRs |
| requiredApprovalTier | string | `T1`…`T4` |
| competitiveBidRequired | boolean | |
| legitException | string | `NONE` \| `RECURRING` \| `BLANKET_PO` \| `SEPARATE_PROJECT` \| `EMERGENCY` \| `STAGGERED_DELIVERY` |
| reasoning | string | ≤ 120 words; cites PR ids and field values only |
| suggestedAction | string | `CONSOLIDATE` \| `ASK_REQUESTER` \| `APPROVE` |

### System prompt rules (keep in `agent/system-prompt.md`)
- Use only the data provided and the policy; never invent PRs, amounts or facts.
- Treat items as one need when they share a project, purpose or delivery window, or are components/accessories of each other.
- Recognise the legitimate exceptions listed under `legitException`.
- Vague justifications ("urgent", "always done this way") don't qualify.
- When evidence is mixed, prefer `LIKELY_SPLIT` + `ASK_REQUESTER` over `NOT_SPLIT`.

### Post-validation script (runs after every agent call)
1. All required fields are present and the enum values are legal.
2. `relatedPrIds` ⊆ input PR ids. Strip any unknown ids and log them.
3. `combinedAmount` = the sum of related PR amounts (±1). Otherwise overwrite it with the computed value and log.
4. `requiredApprovalTier` = the matrix lookup of `combinedAmount`. Otherwise overwrite and log.
5. If validation fails, retry the agent **once** with the error appended. On a second failure, set `verdict = FAILED` and route to a human with the rule evidence only.

## 8. Data model (Data Fabric, tenant-level entities)

Amounts are INR decimals; dates are ISO 8601 strings in Flow variables. Field names are camelCase. **Every enumeration (role, status, verdict, decision…) is a `STRING` field**, not a choice set, so CSV import works; the Flow enforces the values. The authoritative schema is `data/entities.schema.json` (human-readable: `data/entities.md`). The CLI PascalCases record keys in its output (`prId` → `PrId`), so JMESPath filters on `uip df` output use PascalCase.

| Entity | Fields |
|---|---|
| **Employee** | employeeId (PK text), name, email, managerId, costCenter, approvalLimit (decimal), role (choice: Requester, LineManager, DeptHead, CFO, Audit) |
| **Vendor** | vendorId (PK), name, category (choice), isRecurring (bool), contactEmail |
| **BlanketPO** | blanketPoId (PK), vendorId, category, approvedAmount, consumedAmount, validFrom (date), validTo (date), approvedBy |
| **ApprovalMatrix** | tierId (PK: T1–T4), minAmount (inclusive), maxAmount (exclusive, null = no cap), approverRole, quotesRequired (int), rfqRequired (bool) |
| **PurchaseRequisition** | prId (PK), requesterId, costCenter, projectCode (nullable), vendorId, category, description (long text), quantity (int), unitPrice, amount, currency (default INR), deliverySite, blanketPoRef (nullable), isEmergency (bool), createdAt (datetime), status (choice), splitCaseId (nullable) |
| **SplitCase** | caseId (PK), anchorPrId, relatedPrIds (text/JSON), combinedAmount, ruleScore (int), rulePatterns, agentVerdict (choice), agentConfidence, agentLegitException (choice), agentReasoning (long), requiredApprovalTier, requesterJustification (long), humanDecision (choice), humanComment (long), decidedBy, decidedAt (datetime), finalOutcome (choice), runLog (long) |

**PR status values:** Draft, Submitted, UnderReview, OnHold, Unverified, Released, Consolidated, Rejected.
**Decision values:** CONSOLIDATE, APPROVE_SEPARATE, REJECT, FALSE_POSITIVE, ESCALATED.

## 9. Rule engine (`rules/score.js` and the Flow script node)

Pure function, no I/O: `score(anchorPr, recentPrs, context) → ruleResult`. Keep the Flow script and `rules/score.js` identical in logic.

### Candidate selection
Use PRs from the last **30 days**, with status not Draft or Rejected, excluding the anchor. Include a PR if any of these hold:
- same vendorId **and** same requesterId
- same vendorId **and** same costCenter
- same projectCode (non-null)
- same requesterId **and** same category

### Scoring
| Signal | Points | Pattern |
|---|---|---|
| Same vendor + same requester | +25 | P1 |
| Same vendor + different requester, same cost centre | +15 | P5 |
| Combined amount lands in a higher tier than the anchor alone, or exceeds the requester's own limit | +20 | TIER |
| All PRs share one non-null projectCode | +10 | PROJ |
| Every PR is within 85–100% of a tier boundary or the requester limit | +15 | P2 |
| All PRs submitted within 72 h | +10 | P6 |
| Description token-Jaccard similarity ≥ 0.7 | +10 | P3 |
| Requester has ≥ 3 PRs at 90–100% of their limit in 90 days | +10 | P7 |
| Vendor `isRecurring` | −20 | exception |
| All PRs reference the same valid blanket PO | −30 | exception |
| All PRs `isEmergency` | −10 | exception |

`score = clamp(sum, 0, 100)`. P4 (semantically related items) is left to the agent. P8 (vendor-side invoice splitting) is a separate scheduled sweep (optional).

### Output
```json
{ "score": 70, "patterns": ["P1","P2","P6"], "groupPrIds": ["PR-1041","PR-1042","PR-1043"],
  "combinedAmount": 435000, "anchorTier": "T2", "combinedTier": "T2", "crossesTier": false,
  "requesterLimit": 150000, "exceedsRequesterLimit": true }
```

### Routing thresholds
| Score | Path |
|---|---|
| 0–29 | Release + log; **the agent is not called** |
| 30–59 | Agent; may release only if the verdict is `NOT_SPLIT` with a legitException other than `NONE` |
| 60–100 | Agent; **human review is mandatory regardless of verdict** (guardrail) |

## 10. Flow logic

| # | Step | Behaviour |
|---|---|---|
| 0 | Trigger | Manual root (`requisitionId`, `whatIf`) or `onPrCreated` (Data Fabric record created). Non-Submitted PRs end as `NOT_SUBMITTED` unless what-if |
| 1 | Idempotency | If a SplitCase with `anchorPrId = prId` exists → end |
| 2 | Load context | Read PurchaseRequisition (≤ 1000, newest first), Employee, Vendor, ApprovalMatrix, BlanketPO; the rule engine filters by date. A failed read faults the run (no error port); empty reference data → 9U |
| 3 | Rule engine | Script, §9 |
| 4 | Low-risk gate | score < 30 → 9R |
| 5 | Agent judgement | §7 |
| 6 | Validate | §7 post-validation (one retry, then FAILED) |
| 7 | Gateway | See the gateway table below |
| 8a | Requester justification | Coded Action App `SplitSentinelExplain`, outcomes `SubmitExplanation` / `MergeMyPRs` (`ASK_OUTCOMES`), output `justification`. (No timeout available in Flow) |
| 8b | Agent re-evaluation | Same agent, with `requesterJustification` set → validate → gateway (no second justification round) |
| 8c | Approver review | Coded Action App `SplitSentinelReview`, titled with the amount and approver. Outcomes `MergePRs`, `KeepSeparate`, `Reject`, `NotASplit` (`REVIEW_OUTCOMES`); required output `comment`. SLA/escalation is configured in Action Center (Flow has no task timeout) |
| 9C | Consolidate | Related PRs → Consolidated; route for the correct-tier approval |
| 9R | Release | PR → Released |
| 9X | Reject | PR(s) → Rejected |
| 9U | Unverified hold | PR → Unverified; notify procurement ops |
| 10 | Audit | Create/update SplitCase, including a step-by-step `runLog` |
| 11 | Notify | Gmail **draft** to the requester (CC manager on Consolidated/Rejected); skipped on what-if; failure does not block the case |
| 12 | Repeat offender (optional) | ≥ 3 confirmed splits by the requester in 90 d → notify Audit |

### Gateway (step 7)
| Condition | Route |
|---|---|
| NOT_SPLIT, legitException ≠ NONE, score < 60 | 9R |
| NOT_SPLIT, score ≥ 60 | 8c (guardrail) |
| LIKELY_SPLIT, suggestedAction = ASK_REQUESTER, no justification yet | 8a |
| LIKELY_SPLIT (otherwise) | 8c |
| SPLIT | 8c, recommendation CONSOLIDATE |
| FAILED | 8c, rule evidence only |

### Error handling matrix
| Failure | Handling | End state |
|---|---|---|
| Data Fabric read fails | retry ×3 | Unverified hold |
| Rule script throws | log to runLog | approver review |
| Agent error / timeout / invalid output | retry once | FAILED → approver review |
| Agent cites unknown ids / wrong amount or tier | correct + log | continue |
| Requester silent 24 h | continue without justification | approver review |
| Approver silent 48 h | escalate one tier | ESCALATED |
| Gmail send fails | retry ×2, log | case continues |
| Duplicate trigger | idempotency check | skipped |

## 13. Rules for agents working in this repo

- **Source of truth:** `.flow-sdk/SplitSentinel.flow.ts`. Never hand-edit `SplitSentinel.flow`, `resources/`, `bindings.json` or the generated `connectors*/`.
- Run the full check → compile → validate → format loop after every Flow source edit, and before claiming done.
- Keep `rules/score.js` and the Flow script node in sync. Change both or neither.
- Don't commit secrets, tokens, `.auth` files, tenant/org IDs, personal emails or `.venv/`. Use placeholders like `<tenant-id>` in docs.
- Commits: small, descriptive messages. The repo-local author identity is already configured; don't change git config.
- Don't upload, deploy or publish the solution (`uip solution upload/publish/deploy`) unless the user asks.
- Don't create, modify or delete tenant resources outside SplitSentinel's own entities, connections and solution folder.
- Log each meaningful build iteration (goal, change, result) in `docs/claude-code-log.md`.
